Installation de Nextcloud

Dockernginx (Mailcow)MariaDBLet's Encrypt

Nextcloud est hébergé derrière le nginx déjà fourni par Mailcow : un seul reverse proxy sert plusieurs sous-domaines. L'astuce est de laisser Mailcow gérer le certificat et le routage — à condition de ne pas oublier l'IPv6.

Certificat SSL via Mailcow

On ajoute un enregistrement DNS A (et AAAA) pour le sous-domaine cloud, puis on déclare ce domaine dans mailcow.conf pour que l'ACME de Mailcow émette le certificat Let's Encrypt :

sudo nano /opt/mailcow-dockerized/mailcow.conf
# ADDITIONAL_SAN=cloud.privatiq.fr

sudo docker compose restart acme-mailcow

Mailcow détecte le nouveau domaine dans ADDITIONAL_SAN, vérifie la réponse DNS et émet un certificat couvrant tous les domaines.

Le conteneur Nextcloud

services:
  nextcloud-app:
    image: nextcloud:latest
    container_name: nextcloud-app
    restart: unless-stopped
    ports:
      - "172.17.0.1:8080:80"
    volumes:
      - ./nextcloud_data:/var/www/html
    environment:
      - NEXTCLOUD_TRUSTED_DOMAINS=cloud.privatiq.fr
    depends_on:
      - nextcloud-db

  nextcloud-db:
    image: mariadb:10.11
    container_name: nextcloud-db
    restart: unless-stopped
    environment:
      - MYSQL_ROOT_PASSWORD=changeme
      - MYSQL_DATABASE=nextcloud
      - MYSQL_USER=nextcloud
      - MYSQL_PASSWORD=changeme
    volumes:
      - ./nextcloud_db:/var/lib/mysql

Le conteneur n'écoute que sur 172.17.0.1:8080 (bridge Docker) : il n'est pas joignable depuis Internet, seul le nginx de Mailcow y accède. On crée ensuite un vhost nginx dans /opt/mailcow-dockerized/data/conf/nginx/nextcloud.conf qui fait un proxy_pass vers ce port.

Le piège : Nextcloud affiche Mailcow (IPv6)

Symptôme — en ouvrant https://cloud.privatiq.fr, c'est la page de Mailcow qui s'affiche, alors que le vhost Nextcloud est correct.

Cause — le VPS OVH répond en IPv6, or le vhost Nextcloud n'écoutait qu'en IPv4. Nginx recevait la requête sur [::]:443, ne trouvait pas de vhost IPv6 pour cloud.privatiq.fr, et retombait sur le vhost par défaut (Mailcow).

SolutionDéclarer les deux familles d'adresses dans le vhost : listen [::]:80 et listen [::]:443 ssl en plus de l'IPv4, puis recharger nginx. Sur tout VPS avec une adresse IPv6, toujours déclarer les deux directives listen dans les vhosts custom.

Principe du virtual hosting

Un seul couple IP:443 sert tous les services. C'est l'en-tête Host: de la requête HTTP qui permet à nginx de choisir le bon vhost :

Ajouter un nouveau service derrière ce proxy

  1. DNS OVH — enregistrement A (et AAAA) du sous-domaine vers l'IP.
  2. nginx — créer un .conf dans le dossier nginx de Mailcow avec le bon server_name et le proxy_pass vers le port Docker interne.
  3. Docker — exposer le service sur 172.17.0.1:PORT (joignable depuis le conteneur nginx).
  4. Application — déclarer le domaine (pour Nextcloud : NEXTCLOUD_TRUSTED_DOMAINS).
  5. Certificat — ajouter le sous-domaine dans ADDITIONAL_SAN et recréer le conteneur acme.

Mise à jour (Docker)

  1. Sauvegarder la base de données (via mysqldump, en passant par sudo tee et non une redirection > qui s'exécute sans les droits root).
  2. docker compose pull pour télécharger la nouvelle image, puis redémarrer les conteneurs.
  3. Lancer la migration avec occ upgrade (doit se terminer sans erreur).

Vérifications post-mise à jour :

CommandeRésultat attendu
occ statusmaintenance: false, needsDbUpgrade: false
occ checkAucune sortie = aucune erreur
occ app:listToutes les apps actives, sans erreur

On teste ensuite depuis le navigateur (accès, édition Collabora, mails Talk). En cas de problème, on restaure la sauvegarde de la base ; sinon on nettoie les anciennes sauvegardes.
